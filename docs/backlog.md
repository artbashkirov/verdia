## 1. Анализ ответчика по реальным судебным данным

**Статус:** отложено  
**Дата отключения:** 2026-04-28

### Что задумывалось

Раздел в результате генерации, где пользователь видит реальную судебную статистику по конкретному ответчику (физлицу/ИП/ООО/учреждению):
- сколько дел всего;
- в скольких — он ответчик;
- сколько проиграл;
- скорректированный прогноз вероятности на основе этих данных;
- расширенные рекомендации с учётом профиля ответчика.

### Что было реализовано

- Бэкенд-роут `src/app/api/refine-search/route.ts` — принимает данные ответчика (имя/ИНН/город), идёт скрейпером по `sudact.ru` (через VPS-скрейпер), считает статистику и возвращает результат. Также апдейтит запись в `generations.response.defendantAnalysis`.
- Колонка `saved_defendants` в Supabase — кэш по ответчикам пользователя.
- Форма «Уточнить поиск» (`clarificationRequest` + `defendantForm` в `src/app/(chat)/chat/new/page.tsx`) с полями «ФИО/название» и «Город регистрации».
- Блок результата `refinedData` в `src/app/(chat)/chat/new/page.tsx` (строки ~1283–1341 на момент 2026-04-28): три счётчика (всего/как ответчик/проиграно), уточнённая вероятность, дополнительные рекомендации.

### Что было ОТКЛЮЧЕНО (потому что работало некорректно)

AI-галлюцинированный блок «Анализ ответчика»:
- Системный промпт `src/lib/prompts.ts` требовал у GPT генерить поле `defendantAnalysis` с `hasHistory`, `summary`, `riskFactors`, `opportunities` — даже когда у системы НЕТ реальных данных об ответчике.
- Стрим-ручка `src/app/api/generate-stream/route.ts` пересылала это поле во фронт через SSE.
- Фронт `src/app/(chat)/chat/new/page.tsx` рендерил блок «АНАЛИЗ ОТВЕТЧИКА» с галлюцинированными «Возможностями» и «Рисками».

В итоге пользователь видел якобы аналитику по ответчику, которая на деле была общей риторикой по теме иска, придуманной AI. Это вводило в заблуждение и нарушало правило о надёжности данных. Удалено: тип, поле в промпте, SSE-событие, рендер блока.

### Что нужно сделать, чтобы вернуть фичу

1. **UX/дизайн.** Согласовать единый макет «Анализ ответчика»: где он живёт в потоке (после `clarificationRequest` → или вместо него?), как сочетается с `refinedData`, как ведёт себя при пустых результатах скрейпинга.
2. **Никаких галлюцинаций.** Поле `defendantAnalysis` не должно генериться AI напрямую. Только если есть реальные данные от скрейпера — рендерим. Иначе показываем CTA «Уточнить ответчика».
3. **Обработка пустых данных.** Что показываем, если по ответчику не нашлось дел (новый/малоизвестный/некоммерческий)? Сейчас флоу не предусмотрен.
4. **Релевантность.** Дела от скрейпера должны быть отфильтрованы по тематике текущего иска, а не просто «все дела с этим ответчиком». Сейчас фильтра по релевантности нет.
5. **Кэширование.** Использовать `saved_defendants` для повторных запросов. Текущая запись есть, но фронт каждый раз ходит за свежими данными.
6. **Тесты.** Юнит-тесты на `refine-search`: пустой ответчик, ответчик без дел, ответчик с >100 делами, ошибка скрейпера.
7. **Регрессия.** Добавить в `docs/manual-regression.md` сценарии: уточнить ответчика → блок появился; не уточнять → блока нет (никаких выдуманных «Возможностей» и «Рисков»).

### Артефакты, оставшиеся в коде

- `src/app/api/refine-search/route.ts` — рабочий, не трогали. Запись `defendantAnalysis: refinedAnalysis` в `generations.response` сейчас не отображается на фронте, но и не мешает.
- `src/app/(chat)/chat/new/page.tsx` — блок `clarificationRequest` (форма «Уточнить поиск») и блок `refinedData` (статистика после скрейпа) **остаются**. Они работают на реальных данных и не были источником проблемы. При желании можно временно скрыть `clarificationRequest`, чтобы не путать пользователя; решение — за продуктом.
- В БД у части старых генераций уже сохранены поля `response.defendantAnalysis` (галлюцинации). На отображение это не влияет (рендер удалён), но при ретроактивной аналитике это надо учитывать.

## 2. Открытие дела (подача в суд через сервис)

**Статус:** запланировано

### Что задумывается

После того как пользователь сгенерировал документы (исковое заявление, претензию и т.д.), сервис помогает ему **фактически подать дело в суд**, а не только скачать .docx. Возможные варианты реализации:

- **Электронная подача** через ГАС «Правосудие» / «Мой Арбитр» (для арбитражных) — генерация подписанного PDF, инструкция по ЭЦП, либо передача через API при наличии партнёрства.
- **Сопровождение «бумажной» подачи** — расчёт госпошлины, генерация квитанции, инструкция по почтовой/курьерской отправке в нужный суд (мы уже знаем суд из `courtPrediction`).
- **Трекинг статуса дела** — после подачи карточка с прогрессом: принято к производству / назначено заседание / решение / апелляция.

### Что нужно проработать

1. Юридический формат подачи: какие виды дел/исков можно подавать электронно, какие требуют бумаги.
2. Расчёт госпошлины (есть калькуляторы НК РФ ст. 333.19 — можно прикрутить).
3. Подписи: ЭЦП, простая электронная подпись через Госуслуги, факсимиле для бумажных.
4. Платёжный сценарий: оплата госпошлины через сервис (партнёрство с банком/ЮКассой) или платёжка пользователю.
5. Хранение и ретеншн: где и как долго мы держим поданные документы (требования к ПД и адвокатской тайне).
6. Карточка дела: связь с `generations.id` и/или новой таблицей `cases` в Supabase.
7. Юридическая проверка: согласовать с юристом, можем ли мы выступать в роли «представителя по подаче».
8. UX: где встраивается CTA «Подать дело» — после блока документов в чате? отдельная страница `/cases/:id`?

### Зависимости

- Должна быть готова и проверена генерация документов (есть).
- Должен быть готов точный `courtPrediction` (есть, но требует ревизии — особенно адрес/контакты суда).
- Желательно — интеграция с реестром судов (можно тянуть с sudrf.ru).

## 3. Возражения на иск (case_type = objection)

**Статус:** запланировано (частично подготовлено)

### Что задумывается

Сейчас сервис ориентирован на сценарий «истец»: пользователь хочет ЧЕГО-ТО добиться (взыскать долг, оспорить увольнение и т.д.), система помогает подготовить иск.

Симметричный сценарий — пользователь **уже ответчик** по поданному против него иску, и ему нужно подготовить:
- **возражения на исковое заявление** (ст. 149 ГПК РФ);
- **отзыв на иск** в арбитраже (ст. 131 АПК РФ);
- **ходатайство об отмене заочного решения** (ст. 237 ГПК РФ);
- **встречный иск** (ст. 137 ГПК РФ);
- **возражения на судебный приказ** (ст. 129 ГПК РФ).

### Что уже подготовлено

- В `src/lib/case-prompts.ts` есть упоминание `case_type = objection` — для разделения логики анализа со стороны истца и со стороны ответчика.
- Архитектурно `generations.response` поддерживает разные структуры — можно добавить objection-specific поля.

### Что нужно сделать

1. **Определение типа дела на входе.** Сейчас определение неявное. Нужен либо явный селектор «Я истец / Я ответчик», либо классификатор от AI на основе формулировки запроса.
2. **Альтернативный системный промпт** под objection: акцент на ст. 56 ГПК РФ (бремя доказывания), ст. 199 ГК РФ (исковая давность), процессуальные нарушения истца, контр-аргументация по сути.
3. **Альтернативные шаблоны документов:** возражения, отзыв, встречный иск, ходатайство об отмене заочного решения. Сейчас все DOCX-шаблоны заточены под истца.
4. **Альтернативные блоки UI:**
   - вместо «Прогноз успеха иска» → «Прогноз отказа в иске / частичного удовлетворения»;
   - вместо «Рекомендованные действия истцу» → «Линия защиты ответчика»;
   - блок «Сильные/слабые позиции истца» вместо текущего обобщённого анализа.
5. **Особый сценарий: судебный приказ.** Возражение на судебный приказ — это короткий шаблонный документ с жёстким сроком (10 дней). Нужен отдельный мини-флоу: проверка срока, генерация краткого возражения, инструкция по подаче.
6. **Логика сроков.** Возражения часто привязаны к процессуальным срокам (5/10/15/30 дней). Нужно явно их показывать пользователю и предупреждать о пропуске.
7. **Тесты.** Регрессия: проверить, что objection-флоу не ломает claim-флоу и наоборот.

### Зависимости

- В идеале — после стабилизации claim-флоу (генерация, документы, оплата).
- Нужны юридические шаблоны от практикующего юриста — самим придумывать опасно (процессуальные документы должны соответствовать ГПК/АПК).

## 4. Zero-downtime deploy

**Статус:** запланировано  
**Приоритет:** средний (закрывает класс багов «502 во время деплоя»)

### Проблема

Сейчас деплой устроен так (`.github/workflows/deploy.yml` → шаги `build-check` → `deploy`):

1. На VPS: `git pull` → `npm install` → `npm run build` → `pm2 reload verdia`.
2. PM2 запускает приложение в **fork-mode** (1 инстанс, через `start.sh`,
   см. `ecosystem.config.js`).
3. На шаге `pm2 reload` процесс корректно завершается, потом стартует новый
   — окно простоя 1–5 секунд (а если кэш холодный — до 10–30 секунд).
4. В это окно nginx видит, что upstream не отвечает, и без специальной
   настройки возвращает дефолтный «502 Bad Gateway nginx/1.24.0».

Симптом: пользователь открывает сайт во время деплоя и видит чужую
страницу 502 (см. репорт от 2026-04-28, 10:06 утра).

### Что уже сделано (частичные меры, 2026-04-28)

- `pm2 restart` → `pm2 reload --update-env` (graceful shutdown).
- Healthcheck в `deploy.yml` после reload: пинг `/api/health` 30 раз с
  интервалом 1 сек, фейлим деплой если не поднялось → проблема видна
  в Actions, а не «висит молча».
- Создан endpoint `/api/health` (`src/app/api/health/route.ts`).
- Брендированная страница `public/502.html` с автообновлением через
  `/api/health`.
- Инструкция для nginx `docs/nginx-config.md` (`error_page`,
  `proxy_next_upstream`, отдельный `/api/health` без `proxy_intercept_errors`).

Это закрывает «жёсткий» 502 (пользователь видит брендированную страницу
вместо nginx-овой, и она автоматически перезагружается, как только
сервис вернулся), но **окно простоя реально остаётся**.

### Что нужно сделать для полного zero-downtime

1. **Перевести `ecosystem.config.js` на Node-точку входа.** Сейчас стартует
   через bash-скрипт `start.sh`, и PM2 cluster-mode не работает с не-Node
   скриптами. Варианты:
   - стартовать `node node_modules/next/dist/bin/next start -p 3000`
     (или `npm run start` через `pm2-runtime`);
   - переменные из `.env.production` подгружать через `env_file` в
     ecosystem-конфиге или через `next.config.ts` (`loadEnvConfig`).
2. **Включить cluster-mode с 2 инстансами:**
   ```js
   instances: 2,
   exec_mode: 'cluster',
   wait_ready: true,
   listen_timeout: 10000,
   kill_timeout: 5000,
   ```
   - `wait_ready: true` + посыл `process.send('ready')` после старта Next →
     PM2 не убивает старый воркер, пока новый не «ready».
   - 2 инстанса по числу обычно достаточно — в любой момент один из них
     обслуживает.
3. **(Опция-максимум) Blue-green через nginx upstream.** Поднять второй
   pm2-процесс на порту 3001, в nginx `upstream verdia_app { server :3000; server :3001 backup; }`. Деплой по очереди рестартит каждый, второй
   обслуживает. Бесплатно даёт ноль простоя даже при cold-start.
4. **Проверить совместимость Next.js 16 с cluster-mode.** На бумаге —
   полностью stateless, проблем быть не должно. На практике — прогнать
   нагрузочный тест после переключения, проверить, что нет утечек памяти
   на 2x инстансах.
5. **Регрессия.** Добавить в `docs/manual-regression.md` сценарий
   «деплой при открытом сайте» и убедиться, что пользователь не видит
   ни 502, ни сброса формы.

### Зависимости

- Знание содержимого `start.sh` на VPS (что именно он экспортирует и как
  запускает Next).
- Доступ к VPS для безопасного переключения (есть откатный план: вернуть
  старый `ecosystem.config.js` и `pm2 reload`).
- Лимит RAM на VPS — cluster-mode удваивает потребление; если сервер
  слабый, идти не на cluster-mode, а на blue-green с одним инстансом
  каждой версии (RAM растёт умеренно, только в момент перекладки).

## Принципы при возврате этих фич

(Отсылка к `.cursor/rules/reliability.mdc`)

1. **Никаких галлюцинаций под видом фактов.** Если данных нет — не показываем заглушку, показываем пустое состояние или CTA.
2. **Кросс-платформенность.** Каждая фича проверяется на iOS Safari, Android Chrome, Desktop Chrome.
3. **Негативные сценарии.** Тайм-аут, ошибка сети, пустой результат, частичные данные — у каждого должен быть осмысленный UI-стейт.
4. **Тесты.** Юнит-тесты на серверные ручки, регрессия в `docs/manual-regression.md`.
5. **Никаких изменений дизайна без явного указания пользователя.** Все макеты согласовываются отдельно.
