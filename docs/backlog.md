## 1. Анализ ответчика по реальным судебным данным

**Статус:** отложено  
**Дата отключения AI-блока:** 2026-04-28  
**Дата скрытия формы «Уточнить поиск»:** 2026-04-29

### Что задумывалось

Раздел в результате генерации, где пользователь видит реальную судебную статистику по конкретному ответчику (физлицу/ИП/ООО/учреждению):
- сколько дел всего;
- в скольких — он ответчик;
- сколько проиграл;
- скорректированный прогноз вероятности на основе этих данных;
- расширенные рекомендации с учётом профиля ответчика.

### Что было реализовано

- Бэкенд-роут `src/app/api/refine-search/route.ts` — принимает данные ответчика (имя/ИНН/город), идёт скрейпером по `sudact.ru` (через VPS-скрейпер), считает статистику и возвращает результат. Также апдейтит запись в `generations.response.defendantAnalysis`.
- Колонка `saved_defendants` в Supabase — кэш по ответчикам пользователя.
- Форма «Уточнить поиск» (`clarificationRequest` + `defendantForm` в `src/app/(chat)/chat/new/page.tsx`) с полями «ФИО/название» и «Город регистрации».
- Блок результата `refinedData` в `src/app/(chat)/chat/new/page.tsx` (строки ~1283–1341 на момент 2026-04-28): три счётчика (всего/как ответчик/проиграно), уточнённая вероятность, дополнительные рекомендации.

### Что было ОТКЛЮЧЕНО (потому что работало некорректно)

**1) AI-галлюцинированный блок «Анализ ответчика» (отключено 2026-04-28):**
- Системный промпт `src/lib/prompts.ts` требовал у GPT генерить поле `defendantAnalysis` с `hasHistory`, `summary`, `riskFactors`, `opportunities` — даже когда у системы НЕТ реальных данных об ответчике.
- Стрим-ручка `src/app/api/generate-stream/route.ts` пересылала это поле во фронт через SSE.
- Фронт `src/app/(chat)/chat/new/page.tsx` рендерил блок «АНАЛИЗ ОТВЕТЧИКА» с галлюцинированными «Возможностями» и «Рисками».

В итоге пользователь видел якобы аналитику по ответчику, которая на деле была общей риторикой по теме иска, придуманной AI. Это вводило в заблуждение и нарушало правило о надёжности данных. Удалено: тип, поле в промпте, SSE-событие, рендер блока.

**2) Форма «Уточнить поиск» (ФИО ответчика + Город регистрации) (скрыто 2026-04-29):**
- Сама форма (`clarificationRequest` + `defendantForm`) и её результат (`refinedData`) **остаются в коде** и были рабочими — они шли на реальный скрейпер по `sudact.ru`.
- Но без полноценного флоу (валидация ФИО/ИНН, фильтр релевантности, обработка пустых результатов, кэш в `saved_defendants`) форма создавала впечатление, что мы «реально проверяем человека по базам» — чего пока нет.
- Решено: скрыть форму до того момента, как будет подключена база с осмысленным поведением во всех сценариях.
- **Как именно скрыто:** в `src/app/(chat)/chat/new/page.tsx` объявлена module-level константа `const SHOW_CLARIFICATION_FORM: boolean = false;` (~строка 117), и оба рендер-блока обёрнуты в `{SHOW_CLARIFICATION_FORM && clarificationRequest && ...}` (строки ~1190 и ~1233). Логика, состояние (`defendantForm`, `setDefendantForm`, `handleDefendantSubmit`, `isRefining`) и API-роут `/api/refine-search` остались — чтобы при возврате не пересобирать их с нуля.
- **Почему через typed-константу, а не литерал `false`:** при `{false && clarificationRequest && ...}` TypeScript считает блок мёртвым кодом и **не делает narrowing** для `clarificationRequest` внутри JSX → `tsc` падает с `'clarificationRequest' is possibly 'null'` (CI build #99). Явный тип `: boolean` снимает literal-инференцию и возвращает narrowing.

### Что нужно сделать, чтобы вернуть фичу

1. **UX/дизайн.** Согласовать единый макет «Анализ ответчика»: где он живёт в потоке (после `clarificationRequest` → или вместо него?), как сочетается с `refinedData`, как ведёт себя при пустых результатах скрейпинга.
2. **Никаких галлюцинаций.** Поле `defendantAnalysis` не должно генериться AI напрямую. Только если есть реальные данные от скрейпера — рендерим. Иначе показываем CTA «Уточнить ответчика».
3. **Обработка пустых данных.** Что показываем, если по ответчику не нашлось дел (новый/малоизвестный/некоммерческий)? Сейчас флоу не предусмотрен.
4. **Релевантность.** Дела от скрейпера должны быть отфильтрованы по тематике текущего иска, а не просто «все дела с этим ответчиком». Сейчас фильтра по релевантности нет.
5. **Кэширование.** Использовать `saved_defendants` для повторных запросов. Текущая запись есть, но фронт каждый раз ходит за свежими данными.
6. **Тесты.** Юнит-тесты на `refine-search`: пустой ответчик, ответчик без дел, ответчик с >100 делами, ошибка скрейпера.
7. **Регрессия.** Добавить в `docs/manual-regression.md` сценарии: уточнить ответчика → блок появился; не уточнять → блока нет (никаких выдуманных «Возможностей» и «Рисков»).

### Как механически вернуть форму «Уточнить поиск» (когда фича готова)

В `src/app/(chat)/chat/new/page.tsx`:

1. В `src/app/(chat)/chat/new/page.tsx` (~строка 117) поменять `const SHOW_CLARIFICATION_FORM: boolean = false;` на `true`. Этого **достаточно** для возврата формы и разделителя — оба рендер-блока на ~1190 и ~1233 уже завязаны на эту константу.
2. (Опционально) Удалить саму константу и `SHOW_CLARIFICATION_FORM &&` из обоих условий, если решили не оставлять feature-flag.
3. Удалить TODO-комментарий `{/* TODO: вернуть, когда будет подключена база... */}` над блоком формы.
4. Прогнать сценарии регрессии (см. п. 7 выше).
5. Проверить, что бэкенд `src/app/api/generate-stream/route.ts` всё ещё кладёт `clarificationRequest` в response (на момент 2026-04-29 — кладёт, поле просто игнорируется фронтом).

### Артефакты, оставшиеся в коде

- `src/app/api/refine-search/route.ts` — рабочий, не трогали. Запись `defendantAnalysis: refinedAnalysis` в `generations.response` сейчас не отображается на фронте, но и не мешает.
- `src/app/(chat)/chat/new/page.tsx`:
  - Блок `clarificationRequest` (форма «Уточнить поиск») — **скрыт через `{false && ...}`** (2026-04-29). JSX, состояние, обработчики и хендлер `handleDefendantSubmit` — на месте. Возврат — снять обёртку (см. инструкцию выше).
  - Блок `refinedData` (статистика после скрейпа) — остаётся, рендерится при наличии данных. Поскольку форма скрыта, в обычном флоу он не появится; в БД у старых записей `refinedData` нет.
- В БД у части старых генераций уже сохранены поля `response.defendantAnalysis` (галлюцинации). На отображение это не влияет (рендер удалён), но при ретроактивной аналитике это надо учитывать.
- Бэкенд `src/app/api/generate-stream/route.ts` всё ещё генерирует `clarificationRequest` и кладёт его в `response`. Это «мёртвая» запись — фронт её не показывает. При возврате формы — пригодится; если фичу решат полностью снести, надо будет убрать и эту генерацию.

## 2. Открытие дела (подача в суд через сервис)

**Статус:** запланировано

### Что задумывается

После того как пользователь сгенерировал документы (исковое заявление, претензию и т.д.), сервис помогает ему **фактически подать дело в суд**, а не только скачать .docx. Возможные варианты реализации:

- **Электронная подача** через ГАС «Правосудие» / «Мой Арбитр» (для арбитражных) — генерация подписанного PDF, инструкция по ЭЦП, либо передача через API при наличии партнёрства.
- **Сопровождение «бумажной» подачи** — расчёт госпошлины, генерация квитанции, инструкция по почтовой/курьерской отправке в нужный суд (мы уже знаем суд из `courtPrediction`).
- **Трекинг статуса дела** — после подачи карточка с прогрессом: принято к производству / назначено заседание / решение / апелляция.

### Что нужно проработать

1. Юридический формат подачи: какие виды дел/исков можно подавать электронно, какие требуют бумаги.
2. Расчёт госпошлины (есть калькуляторы НК РФ ст. 333.19 — можно прикрутить).
3. Подписи: ЭЦП, простая электронная подпись через Госуслуги, факсимиле для бумажных.
4. Платёжный сценарий: оплата госпошлины через сервис (партнёрство с банком/ЮКассой) или платёжка пользователю.
5. Хранение и ретеншн: где и как долго мы держим поданные документы (требования к ПД и адвокатской тайне).
6. Карточка дела: связь с `generations.id` и/или новой таблицей `cases` в Supabase.
7. Юридическая проверка: согласовать с юристом, можем ли мы выступать в роли «представителя по подаче».
8. UX: где встраивается CTA «Подать дело» — после блока документов в чате? отдельная страница `/cases/:id`?

### Зависимости

- Должна быть готова и проверена генерация документов (есть).
- Должен быть готов точный `courtPrediction` (есть, но требует ревизии — особенно адрес/контакты суда).
- Желательно — интеграция с реестром судов (можно тянуть с sudrf.ru).

## 3. Возражения на иск (case_type = objection)

**Статус:** запланировано (частично подготовлено)

### Что задумывается

Сейчас сервис ориентирован на сценарий «истец»: пользователь хочет ЧЕГО-ТО добиться (взыскать долг, оспорить увольнение и т.д.), система помогает подготовить иск.

Симметричный сценарий — пользователь **уже ответчик** по поданному против него иску, и ему нужно подготовить:
- **возражения на исковое заявление** (ст. 149 ГПК РФ);
- **отзыв на иск** в арбитраже (ст. 131 АПК РФ);
- **ходатайство об отмене заочного решения** (ст. 237 ГПК РФ);
- **встречный иск** (ст. 137 ГПК РФ);
- **возражения на судебный приказ** (ст. 129 ГПК РФ).

### Что уже подготовлено

- В `src/lib/case-prompts.ts` есть упоминание `case_type = objection` — для разделения логики анализа со стороны истца и со стороны ответчика.
- Архитектурно `generations.response` поддерживает разные структуры — можно добавить objection-specific поля.

### Что нужно сделать

1. **Определение типа дела на входе.** Сейчас определение неявное. Нужен либо явный селектор «Я истец / Я ответчик», либо классификатор от AI на основе формулировки запроса.
2. **Альтернативный системный промпт** под objection: акцент на ст. 56 ГПК РФ (бремя доказывания), ст. 199 ГК РФ (исковая давность), процессуальные нарушения истца, контр-аргументация по сути.
3. **Альтернативные шаблоны документов:** возражения, отзыв, встречный иск, ходатайство об отмене заочного решения. Сейчас все DOCX-шаблоны заточены под истца.
4. **Альтернативные блоки UI:**
   - вместо «Прогноз успеха иска» → «Прогноз отказа в иске / частичного удовлетворения»;
   - вместо «Рекомендованные действия истцу» → «Линия защиты ответчика»;
   - блок «Сильные/слабые позиции истца» вместо текущего обобщённого анализа.
5. **Особый сценарий: судебный приказ.** Возражение на судебный приказ — это короткий шаблонный документ с жёстким сроком (10 дней). Нужен отдельный мини-флоу: проверка срока, генерация краткого возражения, инструкция по подаче.
6. **Логика сроков.** Возражения часто привязаны к процессуальным срокам (5/10/15/30 дней). Нужно явно их показывать пользователю и предупреждать о пропуске.
7. **Тесты.** Регрессия: проверить, что objection-флоу не ломает claim-флоу и наоборот.

### Зависимости

- В идеале — после стабилизации claim-флоу (генерация, документы, оплата).
- Нужны юридические шаблоны от практикующего юриста — самим придумывать опасно (процессуальные документы должны соответствовать ГПК/АПК).

## 4. Zero-downtime deploy

**Статус:** ✅ реализовано и применено на VPS  
**Дата завершения кода:** 2026-04-28  
**Дата применения на VPS:** 2026-04-29

### Подтверждённые тесты failover (2026-04-29)

- ✅ `pm2 stop verdia-blue` → `curl /api/health` отдал 200 (через green:3002)
- ✅ `pm2 stop verdia-green` → `curl /api/health` отдал 200 (через blue:3000)
- ✅ `pm2 stop verdia-blue verdia-green` → отдалась брендированная `/502.html`
- ✅ `nginx -T` показывает upstream с двумя серверами и `proxy_next_upstream`
- ✅ pm2 save выполнен — состояние переживёт ребут VPS

### Решение

Выбрана архитектура **blue-green через nginx upstream** (а не PM2 cluster-mode):

- `verdia-blue` — port 3000
- `verdia-green` — port 3002 (3001 занят `verdia-scraper`)
- nginx upstream балансирует между ними и автоматически перекидывает на
  здоровый при сбое второго (`proxy_next_upstream`).
- Деплой делает rolling reload: blue → healthcheck → green → healthcheck.
- В любой момент времени хотя бы один процесс отвечает.

Почему НЕ cluster-mode:
- PM2 cluster-mode не работает с `start.sh` (bash-скрипт). Переписывать
  start.sh на Node-стартап «вслепую» опасно — детали env-загрузки на VPS
  неизвестны.
- Blue-green работает с любым стартом, проще отлаживается, явный rollback.

### Что сделано в репо (2026-04-28)

- `ecosystem.config.js` — два процесса blue/green с `kill_timeout: 10s`
  для graceful завершения SSE/streams.
- `.github/workflows/deploy.yml` — rolling deploy с двумя healthcheck-этапами,
  fail-fast если blue не поднимается (green продолжает работать на старой
  версии).
- `src/app/api/health/route.ts` — health-endpoint.
- `public/502.html` — брендированная страница «Сервис обновляется» (на
  крайний случай падения обоих инстансов).
- `docs/nginx-config.md` — production-конфиг nginx с upstream + failover +
  кастомные страницы 502 + отдельный `/api/health` без перехвата ошибок.
- `docs/migration-blue-green.md` — пошаговая инструкция миграции на VPS:
  start.sh → pm2 → nginx → тесты → откат.

### Что нужно сделать на VPS (один раз)

См. `docs/migration-blue-green.md`. Кратко:

1. Убедиться, что новый код задеплоился (или забрать через `git pull`).
2. Привести `start.sh` к виду, поддерживающему `$PORT` (см. `Шаг 1`).
3. `pm2 delete verdia` → `pm2 start ecosystem.config.js` (запустятся blue + green).
4. Скопировать `public/502.html` в `/var/www/verdia/`.
5. Обновить nginx-конфиг по `docs/nginx-config.md`.
6. Прогнать 5 тестов из `docs/migration-blue-green.md` (failover при
   падении одного, кастомная 502 при падении обоих, реальный деплой).

### Что не покрывается blue-green (для будущих доработок)

- **Падение всей VPS** — пользователь видит `502.html`. Решается
  horizontal failover на второй сервер (отдельная задача, не в этом пункте).
- **Миграции БД с breaking changes** — между blue и green в моменте rolling
  reload секунды две существуют обе версии кода. Если миграция ломает
  совместимость с предыдущей версией — нужен двухфазный деплой
  (совместимая миграция → деплой → миграция-чистка).
- **Кеши Next.js** (`revalidate`, `cache: 'force-cache'`) — могут отдавать
  старый контент. Проверять при использовании на проде.
- **Если RAM на VPS < 1 ГБ свободной** — green можно держать выключенным,
  тогда работает только брендированная 502, не zero-downtime. См. FAQ в
  `docs/migration-blue-green.md`.

## 5. Технический долг и обнаруженные баги

Список вещей, которые нашли по ходу работы над reliability/blue-green
(2026-04-28 / 2026-04-29), но сознательно не чинили в этой итерации,
чтобы не размазывать фокус. Отсортированы по приоритету.

### 5.1. OpenAI embeddings возвращают 403 (приоритет: ВЫСОКИЙ)

**Симптом:** в pm2-логах verdia-blue / verdia-green регулярно появляется:
```
[RAG] OpenAI embedding error: 403
```

**Что это значит:** RAG (поиск по корпусу законов через `pgvector` +
embeddings) **не работает**. Ответы AI становятся менее полезными — нет
точных ссылок на статьи ГК/ГПК/НК, нет цитат, всё на «общем знании»
модели. Пользователь это видит как «AI отвечает в общих словах».

**Возможные причины:**
- API-ключ OpenAI **истёк** или **отозван**.
- Закончился **баланс** на OpenAI (он автоматически блокирует доступ).
- IP VPS попал в **геоблок/чёрный список** OpenAI (редко, но бывает).

**Что сделать:**
1. Проверить статус ключа на https://platform.openai.com/api-keys.
2. Проверить баланс на https://platform.openai.com/usage.
3. Если ключ ок и баланс есть — попробовать вызов вручную с VPS:
   ```bash
   curl https://api.openai.com/v1/embeddings \
     -H "Authorization: Bearer $OPENAI_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"input":"тест","model":"text-embedding-3-small"}'
   ```
   Если 403 → читать тело ответа, там будет конкретная причина.

**Где живёт код:** `src/lib/rag.ts` (или подобное — поискать `embeddings`).
Там же стоит добавить **graceful fallback**: при 403/429 не падать в лог
ошибкой, а возвращать пустые embeddings (отдать ответ AI без RAG-контекста)
и репортить метрику.

### 5.2. Server Action errors у открытых вкладок (приоритет: СРЕДНИЙ)

**Симптом:** в логах:
```
Error: Failed to find Server Action "x". This request might be from an
older or newer deployment.
Read more: https://nextjs.org/docs/messages/failed-to-find-server-action
```

**Что это значит:** То же самое, что ChunkLoadError, но для Next.js
Server Actions (формы, мутации). У вкладки, открытой ДО деплоя, в HTML
сохранён ID action'а, который после нового билда уже не существует.
Сабмит формы → 500.

Сейчас защита частичная: `ChunkErrorRecovery` ловит **chunk** ошибки,
но не Server Action.

**Что сделать:**
- Расширить `src/components/layout/ChunkErrorRecovery.tsx` — добавить в
  `isChunkLoadError` детектирование строки `Failed to find Server Action`
  (или сделать отдельную функцию `isServerActionStaleError`).
- При срабатывании — не reload (страница уже подгружена), а **показать
  toast «Сервис обновился, перезагрузите страницу»** с кнопкой `reload`.
  Reload без подтверждения здесь опасен — пользователь может терять
  заполненную форму.
- Добавить регрессию в `docs/manual-regression.md` раздел 11.3.

### 5.3. Боты сканируют уязвимости (приоритет: СРЕДНИЙ)

**Симптом:** в `/var/log/nginx/error.log` десятки тысяч записей вида:
```
client: 93.123.109.180, server: ai-verdia.ru,
request: "GET /server/.env HTTP/1.1"
request: "GET /actuator/trace HTTP/1.1"
request: "GET /config/master.key HTTP/1.1"
request: "GET /WEB-INF/web.xml HTTP/1.1"
```

**Что это значит:** автоматические сканеры пробуют известные пути для
Spring Boot / Java / .env-файлов. У нас Next.js — все пути возвращают 404,
но:
- засоряет error.log (труднее находить настоящие проблемы);
- бесполезно нагружает upstream (мы делаем SSR на 404-страницу для каждого).

**Что сделать:**
- В nginx (в `deploy/nginx/verdia.conf`) добавить блок раннего отказа:
  ```nginx
  location ~* (\.env|\.git/|\.aws|/actuator|/server/|/config/master\.key|/application\.(properties|yml|yaml)|/bootstrap\.(yml|properties)|/WEB-INF/) {
      access_log off;
      return 444;  # close connection without response
  }
  ```
- Установить `fail2ban` с jail на nginx error.log:
  ```bash
  apt install fail2ban
  ```
  Создать `/etc/fail2ban/jail.local` с правилом банить IP после
  10+ запросов на сканер-пути.
- В будущем — Cloudflare WAF перед nginx, тогда боты вообще не доходят.

### 5.4. WebSocket-заголовки убраны из nginx (приоритет: СРЕДНИЙ — ловушка на будущее)

**Что произошло:** в ходе фикса failover (2026-04-29) из nginx-конфига
убрали `proxy_set_header Upgrade $http_upgrade` и
`proxy_set_header Connection 'upgrade'` — они конфликтовали с
`keepalive` в upstream и блокировали `proxy_next_upstream`.

**Почему это ОК сейчас:** в текущем приложении WebSocket не используется
(Supabase Realtime ходит на свой домен, наш `ai-verdia.ru` обслуживает
только HTTP/SSE).

**Когда станет проблемой:** если решим добавить любой WS-функционал
прямо в Next.js (live-обновления чата, collaboration, etc.). WebSocket
просто не подключится, ошибка в DevTools → Console.

**Что сделать (тогда):**
1. В `deploy/nginx/verdia.conf` вернуть upgrade-заголовки в `location /`.
2. **НЕ возвращать** `keepalive` в upstream — failover сломается.
3. Для отдельных WS-маршрутов (например `/api/ws/...`) сделать
   отдельный location с явными upgrade-заголовками — чтобы основной
   `location /` не страдал.
4. Прогнать тесты failover из `docs/migration-blue-green.md`.

### 5.5. `/etc/nginx/sites-enabled/verdia` был файлом, а не симлинком (приоритет: НИЗКИЙ — задокументировано на будущее)

**Что было:** при миграции 2026-04-29 обнаружили, что
`/etc/nginx/sites-enabled/verdia` — **отдельный файл** (1269 байт от
января 2026), а не симлинк на `/etc/nginx/sites-available/verdia`.
Поэтому все правки `sites-available/verdia` за несколько часов nginx
просто **игнорировал** — он грузил старый файл из `sites-enabled`.

**Что сделали:** удалили старый файл, создали правильный симлинк:
```bash
sudo rm /etc/nginx/sites-enabled/verdia
sudo ln -s /etc/nginx/sites-available/verdia /etc/nginx/sites-enabled/verdia
```

**Урок:** при любых правках nginx-конфига **сразу проверяй**
```bash
sudo nginx -T 2>&1 | grep "configuration file"
```
— это покажет реально загружаемые файлы. Если в выводе фигурирует тот,
который ты редактировал — ок. Если нет — копаем sites-enabled.

**Будущее:** если когда-то восстанавливаемся из VPS-снапшота старше
2026-04-29 — проверить ещё раз, что симлинк правильный.

### 5.6. Шум `Auth session missing!` в логах middleware (приоритет: НИЗКИЙ)

**Симптом:** в pm2-логах постоянно:
```
Error getting user in middleware: Auth session missing!
```

**Что это значит:** при заходе анонимного пользователя на сайт middleware
пытается достать сессию через `supabase.auth.getUser()`, её нет — это
**норма**, но мы это логируем как `console.error`. В результате —
огромное количество шума, в котором сложно искать настоящие проблемы.

**Что сделать:** в `src/lib/supabase/middleware.ts` (или где этот лог)
заменить `console.error` на `console.debug` (или вообще убрать) для
конкретного кейса `Auth session missing` — отличать от настоящих
ошибок (network/timeout) по message.

### 5.7. Мусорные файлы в `/opt/verdia-app/` (приоритет: НИЗКИЙ — гигиена)
