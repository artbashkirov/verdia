# Список потенциальных багов и состояние их устранения

Источник: повторное сканирование кодовой базы 2026-04-28 по принципам из `.cursor/rules/reliability.mdc`.

Уровни:
- **P0** — критично, может полностью сломать UX или потерять данные у части пользователей. Чинить немедленно.
- **P1** — серьёзно, влияет на диагностику, часть пользователей или негативные сценарии. Чинить в этой итерации.
- **P2** — заметно, но не критично. Чинить, если не требует переделки UX.

## P0

### B-01. Хэнг `supabase.auth.getUser()` в `Sidebar`/`MobileSidebar`
**Файлы:** `src/components/layout/Sidebar.tsx`, `src/components/layout/MobileSidebar.tsx`.  
**Симптом:** На мобильных браузерах и в PWA-режиме браузерный Supabase-клиент иногда зависает на refresh-токене. В этих компонентах не было таймаута — `getUser()` мог никогда не зарезолвиться, и тогда `setUser`/`loadChatHistory` не вызывались → пользователь видел бесконечный спиннер истории чатов.  
**Решение:** Создана общая утилита `src/lib/auth-timeout.ts` с `getUserWithTimeout(client, 5000)`. Promise.race с таймаутом, при таймауте — `setIsLoadingHistory(false)` и предупреждение в консоль. Дальше работает кэш истории из `safeGet('chatHistoryCache')`.  
**Статус:** ✅ Исправлено (2026-04-28)

### B-02. `localStorage.setItem` без `try/catch`
**Файлы:** `chat/page.tsx`, `chat/new/page.tsx`, `chat/[id]/page.tsx`, `chat/result/page.tsx`. Sidebar/MobileSidebar были мигрированы ранее.  
**Симптом:** В Safari Private Mode, в некоторых WebView (Telegram/Instagram) и при заполненном хранилище `setItem` бросает `QuotaExceededError`. Так как вызовы синхронные и не были обёрнуты в try/catch — исключение поднималось в обработчик/эффект и ломало рендер дерева React.  
**Решение:** Все клиентские вызовы `localStorage.*` и `sessionStorage.*` заменены на `safeGet`/`safeSet`/`safeRemove` из `src/lib/safe-storage.ts`. В сэйф-обёртках ошибки тихо логируются как `console.warn` и не пробрасываются в React-дерево.  
**Статус:** ✅ Исправлено (2026-04-28)

## P1

### B-03. Пустой `catch` в SSE-обработчике AI-ответа
**Файл:** `src/app/api/generate-stream/route.ts` (~строка 511 до правки).  
**Симптом:** Если AI возвращал битый/обрезанный JSON, catch проглатывал исключение и слал клиенту generic «Ошибка обработки ответа» — в логах сервера ноль информации. Невозможно было диагностировать в проде.  
**Решение:** Catch теперь принимает `parseError`, логирует сообщение, тип ошибки, первые 500 символов сырого ответа и `generationId`. Это позволит воспроизводить и чинить такие случаи.  
**Статус:** ✅ Исправлено (2026-04-28)

### B-04. `fetch` без `AbortController` для длинных операций
**Места:**
- `chat/[id]/page.tsx` — fetchMessages + fetchGeneration с поллингом.
- `Sidebar.tsx` — поллинг генерирующихся.
- `MobileSidebar.tsx` — то же самое.

**Симптом:** При быстром переключении между чатами / уходе со страницы старые fetch'и продолжали идти, и вызывали `setState` на размонтированных компонентах. Лишний трафик + race conditions + варнинги React.  
**Решение:** Везде добавлен `AbortController` с пробросом `signal` в fetch + `controller.abort()` в cleanup-функции эффектов. Ошибки `AbortError` отдельно фильтруются и в логи не попадают.  
**Статус:** ✅ Исправлено (2026-04-28)

### B-05. `alert()` для пользовательских ошибок
**Симптом:** В коде 19 вызовов `alert(...)` для отображения ошибок. На iOS блокирует main thread, выглядит как нативный системный диалог (плохой UX), не вписывается в дизайн-систему.  
**Места:** `chat/new/page.tsx`, `chat/[id]/page.tsx`, `Sidebar.tsx`, `MobileSidebar.tsx`, `cases/new/page.tsx`, `cases/[id]/page.tsx`, `chat/result/page.tsx`, `components/cases/CaseTransitionBanner.tsx`.  
**Решение:** Гибридный подход с библиотекой `sonner`:
- Установлен `sonner` как зависимость.
- Создан `src/components/ui/AppToaster.tsx` — обёртка с настройками: `position="bottom-center"`, `richColors`, `theme="light"`, `duration=4000`, `visibleToasts=3`.
- `<AppToaster />` подключён в root `layout.tsx` внутри `<ThemeProvider>`.
- Все 19 `alert(...)` заменены на `toast.error(...)`.
- В формах с inline-ошибкой (`setError(errorMessage)` в чате) inline-индикатор оставлен — он работает параллельно с тостом (тост — транзитивный фидбэк, inline — постоянный).
**Статус:** ✅ Исправлено (2026-04-28)

## P2

### B-06. `supabase.auth.getUser()` на login page без таймаута
**Файл:** `src/app/(auth)/login/page.tsx`.  
**Симптом:** Та же история, что в B-01. На маунте — fire-and-forget `getUser()` для редиректа уже залогиненного пользователя; если повис на мобильном — пользователь видел форму с задержкой. После неудачного `signInWithPassword` — фолбэк-проверка `getUser()` тоже могла зависнуть.  
**Решение:** Оба вызова заменены на `getUserWithTimeout(supabase)` (5 секунд по умолчанию для маунта, 3 секунды для фолбэка после signIn). При таймауте — корректно показываем форму / сообщение об ошибке.  
**Статус:** ✅ Исправлено (2026-04-28)

### B-07. Прочие чувствительные `getUser()` в браузерных контекстах
**Места:** `verify`, `forgot-password`, `reset-password`, `register`.  
**Проверено:** Эти страницы НЕ вызывают `getUser()` на маунте. Они используют `signUp`/`resetPasswordForEmail`/`resend`/`updateUser` только в обработчиках submit. Эти вызовы не вызывают «вечный лоадер» при висящем refresh-токене, потому что форма остаётся рендериться независимо. `reset-password/page.tsx` использует `getSession()` — это локальный вызов (читает из localStorage), не делает сетевой запрос. Висеть не может.  
**Статус:** ✅ Не требует исправления (false alarm в первоначальном скан-проходе)
